# Milestone 5.5 — Per-Round Flag Rotation + Per-Team Token Auth

**目标**：把 M5 留下的两个紧贴 flag 机制的 deferred 项落地——

1. **Per-round flag rotation**：每个 DEFENSE 相位开始时给每个 (team, challenge) 重植一个新 flag；旧 flag 立即失效（`submit` 之 `UNKNOWN`）。这样一局可以有多次有效攻击，给后续 Scoreboard 提供有意义的时序数据。
2. **Per-team token auth on `/game/flag/submit`**：`game.yaml` 每队加 `token` 字段；HTTP 路径要求 `X-Team-Token` header，从 header 反查 team_id，body 里的 `team_id` 不再被信任。`GameMgr.submit_flag(team_id, flag)` 内部接口保持不变（受信内部调用）。

**显式不做**：agent 真自主跑攻击 loop。理由：agent 在 dev 容器，对手 prod 在 game_net 上，dev 没有路过去——需要 dev→own_prod 的 pivot 通道（SSH 或 RPC），而这个 pivot 通道 design 还没给定义。等 design 给个解再做。M5.5 把 token + rotation 准备好，agent 来的时候直接用。

## 范围

✅ 实现：

- `tests/test_m5_5_rotation.py`：

  - integration：跑 round loop，验证每个 DEFENSE 进入时 FlagStore 里 (team, service) 的 flag 字符串都变了；旧的 round-0 flag 不再可用；FLAG_PLANTED 事件计数 = round 数 × team 数

⬜ 不做（推到 M6 / 后续）：

- **Agent 自主走攻击 loop** —— 需要先定 dev→own_prod 的 pivot 协议（SSH? sidecar? exec-via-prod-RPC?）。design_v1.md §6 没给定义。等 design 决定

- **Phase-gated submission（DEFENSE 期间拒绝 submit）** —— design 没要求；不动

## 关键设计抉择

### 为什么 rotation 用 subscriber 模式，不传 callback 给 RoundLoop

两种实现：

A. **RoundLoop 拿一个 `on_defense_start` callback** —— RoundLoop 直接知道 GameMgr，紧耦合。
B. **GameMgr subscribe `PHASE_CHANGE`** —— RoundLoop 不知道有 rotation 这件事，只发事件；GameMgr 在事件 handler 里做。

B 更符合现有 EventBus 模式（FileSink、WS 都是 subscriber）；RoundLoop 保持只关心相位 + 网络。`bus.publish` 是 sequential await，所以 handler 跑完 plant_flags 才返回，replant 一定在 DEFENSE 计时开始前完成。

### plant_initial_flags 不删

它会被 round-1 DEFENSE 的 replant 立刻覆盖，存在窗口只几毫秒。但保留它的理由：

- M5 测试直接调 `game.plant_initial_flags()`（不跑 round loop），删了会破坏 M5 测试
- 非游戏场景（开发时手动验证）：起容器、装 challenge、植 flag、socket 测一下；这是个有用的独立步骤

代价是几毫秒的"幽灵 flag"。Trade-off 接受。

### token 怎么塞给 agent —— M5.5 不解决

token 在 `game.yaml.teams[].token`，会经 `${VAR}` 展开（如果用占位符）。agent 怎么拿到自己的 token？两种现实路径：

1. 写进 `agent.env`（ClaudeAgentManager 已经写 env file）—— 但要让 manager 知道这个 team 的 token，AgentConfig 得加字段
2. 注入 system prompt

两个都得改 M4 的 `AgentConfig` / `ClaudeAgentManager`。**M5.5 不做这个**：token 字段先在 yaml + Team dataclass + HTTP 层落地；agent 接入留给"agent attack loop" milestone 一并做（那个 milestone 还得设计 pivot 协议）。

### 为什么 BAD_TOKEN 在 API 层、不在 FlagStore

FlagStore 是受信内部状态：调用方 = GameMgr，已经 trust 调用方提供的 team_id。API 层是不可信边界，必须验 token 后才能 derive team_id 给 GameMgr。让 FlagStore 多一个 BAD_TOKEN 路径会污染它的语义。所以：

- API 层：header 验 token，失败直接返回 BAD_TOKEN（不调 GameMgr，也不发 FLAG_SUBMITTED 事件 —— 攻击者拿假 token 探测不应该有事件回声）
- GameMgr.submit_flag：API 验过 token 才会调；之后逻辑保留 M5 的 ACCEPTED/UNKNOWN/OWN/DUPLICATE 四类
- SubmitResult.reason 的合法值集合理论上变成 5 种，但其中 BAD_TOKEN 只由 API 层用，FlagStore 永远不返回

### 攻击者拿假 token 探测：要不要发事件？

不发。理由：

- 事件 = 可观察。BAD_TOKEN 事件会泄露"有人在敲门"给所有面板订阅者；攻击方观察自己 BAD_TOKEN 数 vs ACCEPTED 数能调参数
- BAD_TOKEN 没有有意义的攻防语义（不是合法 flag 提交）
- 服务端日志（uvicorn access log）已经记 401-class 模式，运维有需要时去那看

## API 改动

```
POST /game/flag/submit
Content-Type: application/json
X-Team-Token: dev-team1-token       ← required
{"flag": "FLAG{...}"}               ← body no longer carries team_id

→ 200 {"accepted": true,  "reason": "ACCEPTED"}
→ 200 {"accepted": false, "reason": "BAD_TOKEN"}   (header missing / wrong)
→ 200 {"accepted": false, "reason": "UNKNOWN"}     (flag never planted / rotated out)
→ 200 {"accepted": false, "reason": "OWN"}         (derived team_id == flag owner)
→ 200 {"accepted": false, "reason": "DUPLICATE"}   (same victim already claimed)
```

Body's `team_id` is now ignored — leaving it in old clients is harmless, but it
no longer authoritative. The header is the only authoritative source.

# rotation
def test_plant_flags_rotates():
    game = GameMgr(...)  # 用 mock service that doesn't really PUT
    game.plant_initial_flags()
    old = dict(game.flags.planted)
    game.plant_flags(round_id=1)
    new = dict(game.flags.planted)
    assert set(old.keys()) == set(new.keys())
    for k in old:
        assert old[k] != new[k]              # 字符串变了

## 安全注意

- token 在 dev game.yaml 是明文；正式 match 用 `${API_TEAM_TOKEN_TEAMn}` 占位符 + `.env` —— `_expand_env_vars` 已经支持
- BAD_TOKEN 不发事件：避免事件流变成 token 探测的反馈通道
- body 的 `team_id` 字段忽略掉：不要让旧客户端的 typo 误导服务端
- 旧 flag 在 rotation 后立刻 UNKNOWN：攻击方如果缓存了上一轮的 flag 想"晚一拍"再交，会被 UNKNOWN 拒；这是 feature 不是 bug（迫使攻击者节奏跟上 round loop）
