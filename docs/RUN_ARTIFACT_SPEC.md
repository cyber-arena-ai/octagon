# CyberArena Run Artifact Specification

How one match is laid out on disk. Everything is **static files** — pick a `runs/<ts>/` folder and read it. This describes the structure only; parsing and rendering are up to you.

**Mental model:** one match = one `runs/<ts>/` folder. It has a few **teams**; each team plays a few **rounds**. There are two modes (`config.yaml` → `round_config.mode`):

- **sync** (default): each round has two **phases** — `defense` (harden your own service) then `attack` (break into the opponent's). Each team runs one fresh agent per phase.
- **async**: attack and defense happen simultaneously for the whole match (phase is `LIVE` throughout). Each team runs **one long-lived agent** — usually a single "chunk" spanning the whole game; extra chunks appear only if it exits accidentally (crash/timeout) and is restarted (a clean exit is taken as "done"). A "round" is just a flag-rotation tick.

## Folder layout

```
runs/<ts>/                          # ts = UTC start time, e.g. 20260610T200915Z
├── config.yaml                     # [raw]  verbatim copy of the match config
├── events.jsonl                    # [ours] the match timeline
├── panel.html                      # [ours] the trajectories pre-rendered to a page
├── diagnostics/                    # [ours] optional; present only on a failure
│   ├── dry-run-stderr-<team>.txt    [ours] SCRUBBED tail of the pre-R1 dry-run
│   ├── dry-run-stdout-<team>.txt    [ours] same, for the agent's stdout event stream — written
│   │                                 only when the probe exited without reporting ready, since a
│   │                                 clean exit that never called the tool leaves stderr empty
│   └── dry-run-<name>-<team>.txt    [ours] same contract, for whatever the harness adapter adds
│                                     (`AgentManager.dry_run_diagnostics`): opencode writes
│                                     `dry-run-opencode-serve-<team>.txt`, the tail of its
│                                     persistent server's log — the only place a `run` client that
│                                     exits 0 with empty output leaves its reason
│                                    #        agent's stderr — secrets redacted,
│                                    #        last lines only; a failed-dry-run aid
└── artifacts/<team>/round-<N>/     # e.g. team1/round-1/
    ├── stream-attack.jsonl          [raw]  attack agent's trajectory  (Claude CLI's own output)
    ├── stream-defense.jsonl         [raw]  defense agent's trajectory (Claude CLI's own output)
    ├── metadata-{attack,defense}.json   [ours] per-phase summary: duration, exit code, timed-out
    ├── agent-{attack,defense}.log       [raw]  unparsed CLI log (stdout+stderr)
    └── docker.log                       [raw]  the target service's own logs
```

`[raw]` = exactly what the tool emitted, contents untouched by us. `[ours]` = generated by CyberArena.

**Failure diagnostics (optional).** On a flag-service failure, `artifacts/flag-service.log` holds the facility container's own `docker logs` snapshot — where a `/flags/configure` or `/flags/rotate` **500**'s traceback lives, otherwise lost when the container is torn down. Present only when a flag-service call actually failed.

**Optional `patched-vulbox/` (opt-in).** When the match config sets
`snapshot_patched_vulbox: true` (default off; typical for **solo** runs), each
team's prod container is `docker commit`-ed and `docker save`-d at end of run —
the hardened box, handed off for offline verification (`docker load -i <tar>`,
then run the ground-truth PoC / diff the patch):

```
runs/<ts>/patched-vulbox/
├── <team>-<challenge>.tar      [ours] docker save (--named; keeps the repo:tag)
└── manifest.json               [ours] one entry per snapshot: team, challenge,
                                        base_image, committed_image, tar, size_bytes
```

**Solo-mode result (the canonical outcome — NOT the scoreboard).** A `solo` run
writes one role-tagged result file under `artifacts/` (alongside `metrics.json`);
read THIS, not the `winner`/`score`, which is observational-only in solo. Every
solo result is self-describing — it carries `finished_at` (ISO 8601 UTC — the
verification date), `challenge`, `harness` (the real agent's CLI provider),
`model`, and the time-to-success from game start:

```
runs/<ts>/artifacts/verification.json   [ours] solo_role: defense — {execution_status,
                                        verification_status: verified|unverified|
                                        inconclusive, finished_at, challenge, harness,
                                        model, defense_result: {service_healthy,
                                        verifier_available, post_patch_{blocked,captures,
                                        errors}, final_verifier_result, verified_fixed,
                                        time_to_verify_seconds}}
runs/<ts>/artifacts/attack_result.json  [ours] solo_role: attack — {execution_status,
                                        finished_at, challenge, harness, model,
                                        attack_result: {captured, first_capture_round,
                                        total_captures, time_to_capture_seconds}}
```

`time_to_verify_seconds` / `time_to_capture_seconds` are wall-clock seconds from
game start (the round loop going LIVE — bring-up excluded) to the verified-fix
latch / first accepted capture (`null` if never reached); each is paired with a
human-readable `time_to_verify_hms` / `time_to_capture_hms` (`HH:MM:SS`, hours
uncapped). `GAME_END` also carries
the same object under `payload.solo_result` (absent in
async — absence, not `false`). In **solo-defense** the timeline additionally
carries the Layer-2 verifier signal: `VERIFIER_ATTEMPT_STARTED` /
`VERIFIER_ATTEMPT_RESULT_REPORTED` (one pair per verifier attempt, correlated by
`attempt_id`), `VERIFIER_UNAVAILABLE` (no runnable exploit + `verifier.required:
false`), and `VERIFIER_COMPLETED` (the verified-fix latch that ends the match).
`get_attacks_received` stays a plain cumulative count in ALL modes — it is NOT
augmented with any verifier field.

**Async-mode layout.** In async mode there is no defense/attack split and the agent is long-lived (one continuous agent per team across the whole game), so there is **no `round-<N>` subdirectory** — each team's files live directly under `artifacts/<team>/`, numbered by chunk (one chunk per agent invocation; chunk 0 is the first, later chunks are restarts after an accidental exit):

```
artifacts/
├── agents.json                  [ours] merged trajectory per team (see below)
└── <team>/
    ├── stream-async-<n>.jsonl   [raw]  agent trajectory for chunk <n>
    ├── stream-async-<n>.jsonl.timing  [ours] per-line arrival wall-clock, `<line_no>\t<epoch>`
    ├── agent-async-<n>.log      [raw]  unparsed CLI log (stdout+stderr) for chunk <n>
    ├── metadata-async-<n>.json  [ours] per-chunk summary: duration, exit code, timed-out
    └── docker.log               [raw]  the target service's own logs (snapshotted each rotation tick)
```

## One continuous trajectory per team

An async agent is restarted on any accidental exit, so a team's trajectory is
split across `stream-async-0.jsonl`, `-1`, `-2`, …. Those **raw** per-chunk files
stay as-is (parse them for a verbatim, per-CLI deep-dive). For a single coherent
view, the chunks are also **merged one-trajectory-per-team**: the normalized
transcript cards (`transcripts.py` flattens claude/codex/opencode to one shape),
concatenated in order, with a `chunk_boundary` card between chunks so a restart
stays visible without breaking the single read.

- **Live:** `GET /game/agents` returns `{run, transcripts: [<one merged entry per
  team>]}`. It re-reads the run's files on each call, so polling while the match
  runs reflects the growing current chunk (real-time). Reachable through the
  deploy platform's `/live-panel/{id}/game/agents` proxy.
- **Finished:** the same payload is frozen to `artifacts/agents.json` at run end
  (the live GameMgr is gone once the run ends). The deploy platform serves it at
  `GET /api/jobs/{id}/trajectory`; while a run is live, that trajectory comes
  from `/game/agents` through the platform's generic `/game/*` passthrough
  (`/live-panel/{id}/game/agents`).

A merged entry: `{team_id, phase: "merged", chunks: <N>, stats: {…}, events: [
<cards, with a {kind: "chunk_boundary", …} card between chunks> ]}`. Each card
carries a `ts` (arrival wall-clock, epoch secs, joined by line number from the
`.timing` sidecar; `null` when the sidecar lacks that line) so the **live** feed
has per-event time — not just the finished trajectory.

The same `stream-*.jsonl` schema (below) applies. In `events.jsonl`, async events carry `phase: "LIVE"` and `round_id` = the flag-rotation tick (the timeline still tracks rotations even though artifacts aren't split by round).

## `stream-<phase>.jsonl` — one agent's trajectory

The full record of one agent in one phase, in order. **JSON Lines** (one JSON object per line). Each line has a `type`:

> **Coverage caveat — 6 of 9 harnesses produce a parseable trajectory.**
>
> | harness | `stream-*.jsonl` content | parses to |
> |---|---|---|
> | `claude`, `qwen` | Claude-style `stream-json` | events ✅ |
> | `codex` | `exec --json` | events ✅ |
> | `opencode` | `run --format json` | events ✅ |
> | `kimi` | OpenAI-chat-shaped role/content/tool_calls `stream-json` | events ✅ |
> | `gemini` | Gemini CLI's own `{"type":"init\|message\|tool_use\|tool_result\|result", …}` schema (top-level `role`/`tool_name`, ISO `timestamp`) | events ✅ |
> | `grok` | its own `{"type":"text\|thought\|end\|error","data":…}` NDJSON — **not** this schema, and it carries no tool-call records at all | **0 events** |
> | `nexau` | nothing (a **0-byte** file: the driver only prints a final summary, which the supervisor's SIGKILL usually pre-empts) | **0 events** |
> | `openhands` | human-readable non-JSON SDK log | **0 events** |
>
> A consumer must treat an empty transcript as normal for those three, not as a
> failed match. What degrades with it: the panel trajectory **and** the
> stream-derived metrics in `metrics.json` (`tool_calls`, `n_tool_calls`,
> `tool_latency_p50/p90`). What does **not** degrade: token counts and cost,
> which come from the api-router's `usage-router.jsonl` and are
> provider-agnostic. Each `usage-router.jsonl` row and the per-team
> `metrics.json` summary also record three model names that can legitimately
> differ — `configured_model` (what the operator set in `game.yaml`), `model`
> (what the agent CLI sent on the wire), and `provider_model` / `provider_models`
> (what the provider actually served, e.g. a canonicalized Gemini slug); a
> mismatch is expected, not a config failure. (Lines that are valid JSON but not
> objects are skipped by the parser rather than crashing it.)

| `type` | What it is |
|---|---|
| `system` | session init; the first line names the model & tools |
| `assistant` | the agent's turn — content is in `message.content[]` (blocks below) |
| `user` | results handed back to the agent — tool outputs in `message.content[]` |
| `result` | last line; totals: `num_turns`, `duration_ms`, `total_cost_usd`, `usage` |

The blocks inside `message.content[]`:

| Block | Fields |
|---|---|
| `thinking` | `thinking` |
| `text` | `text` |
| `tool_use` | `name`, `input`, `id` |
| `tool_result` *(in a `user` line)* | `tool_use_id`, `content`, `is_error` |

Per-turn token counts are in `message.usage` (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`).

The schema above is Claude's. The file is **whatever the team's agent CLI emits**, so two other shapes also appear (both flattened to the same transcript cards by `transcripts.py`):

- **codex** (`codex exec --json`): dotted top-level `type` — `thread.started` / `turn.{started,completed}` / `item.{started,completed}` (item `type` ∈ `agent_message` | `reasoning` | `command_execution` | `mcp_tool_call` | `file_change`); usage rides `turn.completed`.
- **opencode** (`opencode run --format json`): one event per line wrapping a `part` object with a top-level `sessionID`; `type` ∈ `text` | `tool_use` | `step_start` | `step_finish` | `reasoning`. Tool calls carry `part.state.{input,output,status}`; per-step tokens are on `step_finish` (`part.tokens`). **Reasoning backfill:** headless `--format json` counts reasoning tokens but never emits the `reasoning` **text** on stdout (opencode #27361), so `OpenCodeAgentManager.run_phase` reads it back from the still-running server session (`GET /session/<id>/message`) and folds each `reasoning` part into the stream (before its `messageID`'s first line) — the `reasoning` lines here are that backfill, not raw CLI output.

> [gamemgr/transcripts.py](../gamemgr/transcripts.py) is one example of flattening all three shapes, for reference.

## `events.jsonl` — the match timeline

JSON Lines, one event per line: `{ ts, type, team_id, round_id, phase, payload }`. The event types:

- `FLAG_SUBMITTED` — a capture; `payload.accepted` says whether it counted. `payload.store` names the objective slot, and `payload.outcome` (`read` / `write` / `execute`) + `payload.scope` (registered attack-scope id) + `payload.oracle` (`submit` / `claim`) say WHICH capability was measured and how. `oracle: "claim"` rows come from `POST /game/flag/claim` — the attacker placed a mark the facility then read back — and use the same event shape on purpose. Neither flags nor marks ever appear in the payload.
- `FLAG_PLANTED` — a fresh flag went live for a team that round; `payload.attempt` (which try it landed on, 1 = first) + `payload.latency_ms` (the plant's SSH round-trip) help explain a slow rotation.
- `FLAG_PLANT_FAILED` — that team's plant never succeeded that round (box down through the plant window, retries exhausted); `payload.attempts` + `payload.error`. Signals the flag did **not** rotate — exclude the round from scoring analysis.
- `ROUND_START` / `ROUND_STOP` / `PHASE_CHANGE` — round and phase boundaries.
- `AGENT_TIMEOUT` — an agent ran out of time that phase.
- `SERVICE_HEALTH_CHECK` — periodic health ping (emitted frequently).
- setup/deploy/restart events — `SETUP_*`, `SERVICE_DEPLOYED`, `SERVICE_RESTART_*`, etc.

## `config.yaml` — the match setup

A verbatim copy of the config this match ran with. Key fields:

- **Teams & models** — `teams[].id`, `teams[].agent.model`
- **Challenge** — `challenges[].name` / `.type` / `.port`, `challenges[].deploy_on`
- **Rounds & timing** — `round_config.total_rounds`; sync: `round_config.defense_secs` / `.attack_secs`; async: `round_config.mode: async` + `round_config.round_secs` (flag-rotation interval)

`*_secs` is the budgeted time; the actual time each phase/chunk took is in that phase's `metadata` (`duration_ms`). No secrets — API keys stay as `${...}` placeholders.
